## QA-03: fallback не раскрывает конфликт характеристик — P1

Тест: ChatAcceptance.test_B10_fallback_must_disclose_conflicting_characteristics.
Источник требования: указание владельца сообщать расхождения EKT.
Mock detail: name «Автомат 160А», properties.NOMINALNYY_TOK «250 А».
Без LLM отправить «Какой ток у 200300285_?».
Факт: «Автомат 160А. Цена: 100. Остаток: 3. Данные получены из EKT.»
Нет предупреждения и второго значения. Ожидание: раскрыть оба значения и расхождение.
Это пробел относительно AI-требования: минимальный fallback-контракт описывает
вывод только name/price/quantity.

## QA-04: платёжный номер сохраняется в истории — P0

Тест: ChatAcceptance.test_B18_payment_data_must_not_be_saved_in_history.
Источник: requirements.md §9 запрещает хранить платёжные данные.
Пользователь просит сохранить синтетический тестовый номер карты. Mock LLM отказывает,
но номер остаётся в ChatService.sessions[session_id].turns.
Ожидание: исключить реквизиты из сохраняемой истории. Реальные клиентские данные
не использовались. Речь о памяти процесса, а не установленной записи на диск/в SQLite.

## QA-05: аналог при внутреннем конфликте карточки — P1

Тест: AnalogAcceptance.test_D06_same_name_with_conflicting_source_is_not_safe_evidence.
Исходник quantity=0, кандидат=5. Оба name «Автомат 160A 400V», у обоих
properties.NOMINALNYY_TOK «250 А». Запрос «Предложи аналог 200300285_».
Факт: fallback возвращает кандидата по совпадению названий без раскрытия конфликта.
Строгая QA-политика ожидает отсутствие рекомендации до разрешения противоречия.
Допустимость отдельного непроверенного кандидата с предупреждением надо согласовать
с владельцем. Текущая эвристика соответствует описанному сравнению названий,
но не закрывает требование о конфликтующих данных.

## QA-06: недостоверный текст модели проходит в message — P0

Тест: BoundaryAcceptance.test_F03_false_model_facts_must_not_reach_customer.
Mock LLM без tools возвращает цену 1, остаток 999 и выдуманный URL сертификата.
Факт: HTTP 200, текст без изменений, products=[]. Ожидание строгой AI-приёмки:
неподтверждённые сведения не должны попадать клиенту.
Это проверка отсутствия серверной защиты от ошибочного ответа, не доказательство,
что живая модель обязательно так ответит. Контракт гарантирует происхождение
структурированных products и честно оговаривает ограничения инструкций модели.
Требование «никогда не выдумывать» полностью не обеспечено; решение за AI/backend.

## Ограничения

Ни один тест больше не ждёт /api/chat или demo-cart. C01–C08 проходят, дополнительно
проверены изоляция сессий, сброс pending при ошибке и суммарный остаток.
Живая LLM требует отдельных проверок intent, уточнений и достоверности формулировок.
Источники сертификатов/условий покупки, настоящая корзина/checkout, вложения и
latency не покрываются этим офлайн-прогоном. Main не мержился.
