# EKT.kz — backend каталога

Python + FastAPI: получение списка, карточки товара и поиск по каталогу EKT через Basic Auth. Добавлен минимальный AI-чат на OpenAI Responses API; frontend, корзина, аналоги и вложения пока не реализованы.

## Устройство

- `backend/main.py` — FastAPI, три GET-маршрута и POST /api/chat.
- `backend/config.py` — настройки из `.env` в корне; переменные окружения имеют приоритет.
- `backend/ekt_service.py` — EktService, запросы к EKT и обработка ошибок.
- `requirements.txt` — зависимости.
- `tests/test_backend.py` — проверки без сети и реальных credentials.
- `backend/catalog.py` — локальный каталог SQLite и поиск.
- `backend/sync_catalog.py` — ручная синхронизация каталога.
- `tests/test_search.py` — синхронизация, сохранность каталога и локальный поиск.

Браузер → FastAPI (проверка параметров) → EktService (Basic Auth) → EKT API → JSON → браузер. HTTP-клиент создаётся при запуске и закрывается при остановке. Credentials не передаются в ответах или URL; тела ошибок EKT наружу не возвращаются.

Список EKT имеет поля `page`, `per_page`, `count`, `items`. Товары содержат `id`, `name`, `article` и дополнительные поля. Список и карточка возвращаются без преобразования. GET-запросы проверены на реальном API. Снимок каталога для поиска хранится в `data/catalog.sqlite3` (файл исключён из Git). SQLite входит в стандартную библиотеку Python; новых зависимостей нет.

## Локальный запуск (macOS / Linux)

Из корня репозитория, Python 3.9 или новее:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp -n .env.example .env
```

Заполните локальный `.env` реквизитами организаторов:

```dotenv
EKT_API_BASE_URL=https://ekt.kz/api
EKT_API_USERNAME="выданный_логин"
EKT_API_PASSWORD="выданный_пароль"
```

Подсказки выше нужно заменить настоящими значениями. `.env` исключён из Git. Не добавляйте исходный документ с реквизитами в репозиторий.

```bash
python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

После изменения `.env` перезапустите сервер. Без credentials сервер и Swagger запускаются. Credentials нужны для синхронизации и прямых запросов списка/карточки EKT. Поиск по уже загруженной SQLite работает без credentials и без сети.

## Проверка в браузере

- Первая страница: http://localhost:8000/api/products
- Вторая страница: http://localhost:8000/api/products?page=2
- Товар: http://localhost:8000/api/products/detail?id=515291
- Swagger: http://localhost:8000/docs

`page` по умолчанию 1, `id` обязателен; оба — положительные целые числа. Некорректные параметры дают 422 без обращения к EKT.

Ошибки возвращаются как `{"detail": "описание"}`:

| HTTP backend | Причина |
| --- | --- |
| 503 | Нет credentials или EKT вернул 429 |
| 504 | Таймаут EKT: 5 секунд на соединение, 15 на остальные сетевые операции |
| 404 | EKT вернул 404 |
| 502 | Ошибка сети, авторизации EKT, другой неуспешный статус или некорректный JSON |

Редиректы не выполняются автоматически. Товар `515291` найден на второй странице: артикул `200300285_`, название `027228 АВ DRX250 MT 3ф 160А 18ka Legrand (1)`. Наличие на складе отдельно не проверялось.

## Синхронизация и локальный поиск

Контракт для frontend с точными примерами ответов: [api-contract.md](api-contract.md).
CORS разрешён только для `http://127.0.0.1:5173`, методы GET/POST, без credentials.

Перед первым поиском и для ручного обновления выполните из корня проекта:

```bash
source .venv/bin/activate
python -m backend.sync_catalog
```

Команда последовательно читает страницы EKT через существующий EktService. Это может занять минуты; прогресс выводится в терминал. Завершение — пустая страница или повтор первой страницы (фактическое поведение EKT за границами каталога). Повтор промежуточной страницы или предел 10 000 страниц считаются ошибкой. Для синхронизации таймаут чтения составляет 60 секунд (обычные endpoints сохраняют 15 секунд), соединения — 5 секунд. При временных ошибках запрос страницы повторяется до двух раз с паузами 3 и 6 секунд. Сообщения различают таймаут соединения и ожидания ответа.

Данные хранятся в `data/catalog.sqlite3`: `id`, `name`, `article`, `price`, `image`, `url`, `url_api_detail`. Дополнительные служебные столбцы содержат нормализованный текст поиска; отдельная таблица — время синхронизации, число страниц и товаров. Повторные ID обновляются, удалённые из EKT товары исчезают после следующей успешной синхронизации.

Все изменения публикуются одной транзакцией только после полного обхода. При ошибке или Ctrl+C предыдущий каталог остаётся доступен. Во время загрузки поиск видит предыдущую версию. Не запускайте несколько синхронизаций одновременно. После обновления перезапуск backend не нужен. При изменении самого EKT во время обхода единый снимок на стороне EKT не гарантирован.

По умолчанию путь базы привязан к корню проекта. Необязательно можно задать `CATALOG_DB_PATH` в `.env` (желательно абсолютный путь). Одинаковый путь используется командой синхронизации и сервером. Файлы SQLite и журналы исключены из Git.

`GET /api/products/search?q=...` читает **только SQLite** и не вызывает ни список EKT, ни detail. Перед первой успешной синхронизацией отвечает 503 с подсказкой команды. Поиск не запускает автоматическую загрузку.

- Поиск по названию и артикулу без учёта регистра, включая кириллицу (Python `casefold`).
- Точное совпадение артикула имеет приоритет: возвращаются все товары с таким артикулом в локальном каталоге.
- Если точного артикула нет — поиск буквальной подстроки в `name` и `article`. Символы `%` и `_` не являются шаблонами.
- Внешние пробелы запроса удаляются; пустой запрос или более 200 символов дают 422.

JSON: `query`, `match_type`, `count`, `items` (семь сохранённых полей), `source="sqlite"`, `synced_at`, `pages_scanned=0`, `catalog_complete=true`. Последние два поля оставлены для совместимости: при поиске страницы EKT не читаются, поиск идёт по последнему успешно загруженному каталогу. `synced_at` показывает его свежесть. Цены — на момент синхронизации; актуализация через detail в этот этап не входит.

Проверка:

- http://localhost:8000/api/products/search?q=200300285_
- http://localhost:8000/api/products/search?q=Legrand
- http://localhost:8000/api/products/search?q=EKT_NO_MATCH_9d013b

Серверный поиск EKT не подтверждён. Обход страниц используется только в команде синхронизации. Точный артикул ищется по индексу SQLite; подстрока — по локальным нормализованным столбцам, без сетевых задержек.

## Автоматические проверки

```bash
python -m unittest discover -s tests -v
```

Проверки используют HTTPX MockTransport и фиктивные значения. Они не обращаются к EKT и не читают реальный `.env`.

Замер 23.09.2026: временная SQLite с 20 000 синтетических товаров, 30 запросов каждого типа через FastAPI TestClient после прогрева. Медиана: точный артикул — 0,74 мс, название (111 результатов) — 2,80 мс, отсутствующий товар — 2,66 мс. Это локальный замер без TCP и браузера, не гарантия времени на другом оборудовании. Тестовые данные в рабочую базу не записывались.

Повторная реальная синхронизация 23.09.2026 завершилась успешно: 15 037 товаров, 752 страницы. Число строк проверено в SQLite. Замер через FastAPI TestClient на этой базе (30 запросов после прогрева): артикул `200300285_` — 1 результат, медиана 0,77 мс; `Legrand` — 668 результатов, медиана 8,53 мс. Первый запрос занял соответственно 3,62 и 9,07 мс.

Диагностика прежних таймаутов: CLI и FastAPI использовали один EktService с одинаковым таймаутом чтения 15 секунд. Различий авторизации или HTTP-клиента не найдено. Контрольный запрос установил TCP/TLS за 0,11 секунды и получил ответ за 6,02 секунды. Прежний сбой не воспроизвёлся; его точная сетевая фаза не была записана. Для устойчивости длительной синхронизации таймаут чтения повышен до 60 секунд только в CLI, повторы ограничены тремя попытками с паузами 3/6 секунд. Теперь ошибки различают соединение и ожидание ответа. Таймауты обычных endpoints не изменены.
